## P0 — обычная отправка удаляет голос из очереди Asterisk

OWNER: `services/voice_gateway/main.py::_send_inject_payload`, `packages/voice_runtime/call_actor.py::_on_playback_drained`.

В конфигурации по умолчанию `IMVERA_INJECT_STREAM_FLUSH=1`, интервал равен 4. После каждых четырёх отправок шлюз отправляет `FLUSH_MEDIA`. Та же операция вызывается в конце обычной фразы. У Asterisk это команда **удалить ещё не проигранное аудио**, а не допередать его. Одновременно новый `telephony_stream=True` убрал ожидание между кадрами, поэтому очередь Asterisk может содержать существенную часть фразы, когда приходит команда удаления.

Регрессия на фактической функции: 8 обычных аудиопакетов без перебивания → **2 FLUSH_MEDIA**. Должно быть 0. Это воспроизведено с transport double, не с настоящей АТС.

Исправление:

1. Убрать периодический FLUSH_MEDIA из нормальной отправки, включая priming.
2. Разделить завершение и отмену: `finish_playback(generation_id)` дополняет/допередаёт последний полный кадр, ставит media mark и ожидает его подтверждение; `abort_playback(generation_id)` выбрасывает локальные остатки и удаляет PBX-очередь.
3. При barge-in не отправлять накопленный хвост старого поколения перед отменой — текущий callback `flush()` это делает.
4. Перед отправкой маркера зарегистрировать ожидание ACK. Соотносить ответ по call/channel/generation/correlation_id; отмена инвалидирует ожидание старого поколения. Таймаут ACK — техническая ошибка, не «доставлено».
5. Обрабатывать MEDIA_XOFF/XON и ограничивать очередь. Не заменять её контролируемое опустошение серией FLUSH_MEDIA.
6. `playback.completed`, сохранение полностью произнесённой фразы и hangup — после подтверждения обработки финального звука АТС. ACK АТС подтверждает обработку в АТС; фактическая слышимость телефона всё равно проверяется записью принимающей стороны.

Одного переключения `IMVERA_INJECT_STREAM_FLUSH=0` недостаточно для окончательного исправления: сейчас этот флаг влияет и на отмену. Разделить семантику API, а не переименовать команду.

Документация: https://docs.asterisk.org/Configuration/Channel-Drivers/WebSocket/#flush_media1

## P0 — входной MEDIA_START меняет формат выходного канала

OWNER: `services/voice_gateway/main.py::_attach_leg`.

Текущий `asterisk_app` создаёт capture=`slin16` (16 kHz PCM) и inject=`ulaw` (8 kHz). Однако общая обработка MEDIA_START безусловно присваивает `inject_sample_rate`, `inject_frame_size`, `inject_encoding`, даже если событие пришло из capture. При порядке «сначала inject, затем capture» шлюз начинает считать выход PCM 16 kHz, хотя реальный inject-канал остаётся ulaw 8 kHz.

Регрессия: исходный inject `(8000, ulaw, 160)` после capture MEDIA_START превращается в `(16000, slin16, 640)`. Это воспроизведено на фактическом `_attach_leg`.

Исправление:

- Обновлять только формат роли события. У capture и inject должны быть отдельные неизменяемые AudioFormat, включая encoding/sample_rate/frame_bytes/ptime.
- Привязывать роль к подтверждённому channel_id конкретного вызова; порядок подключения не должен менять результат.
- Запускать медиа после готовности обоих форматов и подтверждения подключения каналов к мостам.
- Добавить проверку обоих порядков MEDIA_START с различными форматами. Изменение формата после старта обрабатывать явно, не перезаписывать его незаметно.

## P0 — входящая речь 16 kHz преобразуется как будто она 8 kHz

OWNER: `packages/voice_runtime/call_actor.py::on_media_ready`, `_ensure_audio_chain`, `_on_pcm`.

Gateway передаёт в `on_media_ready` частоту **выхода** inject. Внутри этим значением создаётся `_input_resampler`. Когда приходит настоящий capture 16 kHz, `_ensure_audio_chain` уже не обновляет ресемплер. В актуальной топологии корректный inject 8 kHz означает неверное удвоение длительности входящего звука перед VAD/STT.

Регрессия: после готовности inject 8 kHz входной capture кадр 640 байт / 20 ms / 16 kHz превращается в **1280 байт / 40 ms / 16 kHz**. Это воспроизведено на фактическом CallActor с подменённым VAD, который только считает полученные байты.

Исправление:

- Передавать capture и inject форматы отдельно.
- Создавать input resampler только из фактического capture rate; output resampler — из TTS rate в inject rate.
- Сохранять одинаковую физическую длительность до/после преобразования: 20 ms capture должны оставаться 20 ms.
- Перепроверить потоковую фазу текущего `StatefulResampler`: он сохраняет остаток байтов, но не дробную позицию между полноценными чанками. Проверить chunk invariance с учётом задержки/финализации выбранного ресемплера.

## Поправка к прежнему аудиту

Ранее на `dbfd177` было воспроизведено 1,44 s фиксированных ожиданий на 1 s звука при определённой нарезке. В **текущем** `f71de9d` задержка между кадрами для telephony_stream убрана, а gateway накапливает PCM до размера выходного кадра. Поэтому прежний результат нельзя переносить на текущий SIP-путь. Приоритет текущего исправления — три дефекта выше, а не возврат старого pacing вслепую.
