# Scaling & Observability — подробный дизайн (замеры 2026-09-26)

## 0. Закон одной фразой

Вера — заботливый протокол ухода по телефону с доказуемыми гарантиями.
Диалог дешёвый и детерминированный; нагрузка зависит от STT/TTS/GPU, понимания речи, очередей
и телефонии; наблюдаемость покупается бюджетом, а не «всегда всё».
Полный закон: ADR-022. Здесь — детали и замеры.

## 1. Актуальные измерения и граница доказательств — 2026-10-04

[Полный отчёт и исходные измерения](evaluation/multi-complaint-2026-10-04/README.md).
Старый `capacity_probe.py` отбрасывал распознанный текст, подставлял заданные
ответы и синтезировал постоянную фразу. Поэтому опубликованный здесь ранее
вывод «4 параллельных полных звонка» не доказан. Исторические числа
1:675/961ms, 2:539/844ms, 4:718/1508ms, 8:1114/2029ms описывали ту
синтетическую нагрузку; исходный `.run/capacity_probe.json` здесь отсутствует.
Они не принимают production admission, разговор или текущее железо.

Новая реальная проба: один Linux GigaAM v3 RNNT CPU-воркер, quota2CPU/4GiB,
24 запроса на уровень, один репозиторный WAV4.088s. Измерение включает HTTP
клиент, очередь и распознавание; не SIP/TTS или время первого звука Веры.

| Одновременные клиенты | Успешно / всего | p50 / p95 успешных HTTP | HTTP429 |
|---|---:|---:|---:|
| 1 | 24/24 | 640 /683ms | 0 |
| 2 | 24/24 | 1005 /1267ms | 0 |
| 4 | 24/24 | 2099 /2356ms | 0 |
| 8 | 4/24 | 1726 /2462ms | 20 |

Docker working-set после прогрева1.455GiB, после нагрузки1.461GiB;
это не peak RSS, не GPU-память и не RAM всей системы. Best observed successful
rate1.889req/s — throughput этой короткой нагрузки, не гарантированная ёмкость.
`max_active_calls: 1` в production-профилях остаётся неизменным.
Два HTTP TTS-адаптера над одним Qwen backend не являются двумя вычислительными
репликами. Большая очередь увеличит задержку, а не мощность.

Исправленный полный HTTP/SDK probe требует явных endpoints и ordered WAVs:

```sh
IMVERA_DIALOGUE_ENGINE=1 IMVERA_OBS_MODE=pilot python3 scripts/capacity_probe.py \
  --levels 1 2 4 8 --stt "$PROBE_STT_URL" --tts "$PROBE_TTS_URL" \
  --wav "$PROBE_IDENTITY_WAV" "$PROBE_CONSENT_WAV" "$PROBE_COMPLAINT_WAV" \
  --output .run/capacity-probe-actual.json
```

Он передаёт настоящий STT.text/asr_quality в SDK без принудительной установки
consent/identity и синтезирует validated canonical speech. FirstPCM и completePCM
учитываются отдельно, ошибки сохраняются. Доставка моделируется: это всё ещё
не CallActor/FreeSWITCH и не phone audibility. Повторять на выделенных репликах,
не посылать синтетическую нагрузку в текущий обслуживающий звонки стек.

## 2. Тиры наблюдаемости (реализовано, ADR-022)

| | DEBUG (lab) | PILOT | PROD |
|---|---|---|---|
| JSONL | всё | всё кроме `stage.timing` | ошибки + lifecycle |
| STT dumps / forensic wav | on | off | off |
| Бюджет | нет | 200 событий / 64KB на звонок | то же |
| При превышении | — | маркер `trace.truncated` + счётчик | то же |
| Summary звонка | по запросу | `call.summary` всегда | всегда |
| Метрики | — | `/health`: queued/dropped/truncated | + time-series (след.) |

Переключение: `IMVERA_OBS_MODE`. Дефолт `debug` — поведение лабы не
менялось. Ошибки (`*failed*`, `*timeout*`, `*degraded*`, `*TECHNICAL*`)
не фильтруются ни в одном тире. Дропы очереди и трункации — в `/health`
и в алерты, никогда молча.

Живой пример: `fs-5b509b4f` — 222 события / 63KB, из них 171
`stage.timing`. В pilot это ~50 событий, в prod ~15 + summary.

## 3. Куда дальше (по зависимости, не по красоте)

1. **Capacity gate**: `max_active_calls` остаётся 1, пока проба не покажет
   чистые 10 на железе. Поднимать вслепую запрещено.
2. **Реплики STT/TTS**: URLs уже списком; добавлять копии по данным пробы
   (отдельные model-owning процессы/GPU; два HTTP endpoint не доказывают две реплики).
3. **N bridge-процессов + sticky по `fs_uuid`** — когда упрёмся в GIL
   (проба пока упирается в воркеры, не в мост).
4. **Protocol-as-data (YAML)**: short/full/complaint → required slots →
   status. Убирает класс «plans не спросили / severity не спросили».
5. **PhraseSelect одним модулем** (ADR-021 P1).
6. **Отдельный sink** (Loki/ClickHouse) вместо `.run` на диске с Postgres.
7. **100+ concurrent** — только после pilot evidence, отдельным ADR.

## 4. Что НЕ делать (запреты)

- Полный forensic в проде; тихий cloud STT; четвёртый dialogue brain;
- LLM в пути речи; «архитектуру на 100k» до pilot evidence;
- поднимать капы без замера; чинить нагрузку новым мозгом.

## 5. Открытые вопросы владельцу

- Целевой concurrent пилота (5? 10?) и железо под него (второй GPU?).
- Retention аудио (только RED/жалобы? сколько дней?).
- Куда слать метрики (какой стек мониторинга принят?).
