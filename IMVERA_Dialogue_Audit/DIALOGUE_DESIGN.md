# IMVERA — проект диалогового движка и голосовой приёмки

Дата: 6 сентября 2026. Основание: запрос Даниила, фактический код `f71de9d8ba36609b116eb24dd63c7e88a94c05d7`, правила проекта. Статус: проект для реализации; работоспособность предлагаемых изменений ещё не проверена.

## 1. Продуктовый результат

Вера — голосовой помощник для спокойного, уважительного разговора с пожилым человеком. Цель: понять, как проходит его день, корректно собрать сказанное и сохранить результат. Её задача включает поддержание разговора, вопросы пользователя, исправления и право отказаться. Успех не равен заполнению четырёх полей любой ценой.

[Сайт IMVERA](https://imvera.ru/) описывает обычный телефонный контакт и адаптацию вопросов к ответам. Семейные уведомления на сайте относятся к более широкому продукту. В текущем задании проверяется голосовой разговор и сохранение наблюдений, а не работоспособность всех заявлений сайта.

Вера представляется голосовым помощником, не выдаёт себя за родственника или человека. Обращение — на «вы», без уменьшительных обращений по умолчанию. Обычно одна-две короткие фразы, один вопрос; уместная реакция на сказанное вместо одинакового «спасибо» после каждого ответа.

Нельзя обещать помощь, безопасность, вызов службы, передачу сообщения или ответ семьи. «Записала» разрешено только после успешного сохранения соответствующего факта. Если функция недоступна, Вера кратко и правдиво объясняет ограничение. Просьба перезвонить не означает, что обратный звонок назначен.

## 2. Что проверено и почему смена промпта недостаточна

Снимок проверен на актуальной ветке через GitHub. Штатный набор: `103 passed, 2 skipped` (PostgreSQL). Дополнительный набор: `10 failed, 3 passed`. Тесты задают структурированный смысл напрямую в тот же переход SemanticPayload → bridge → CallSession, который использует голосовой путь. Они не используют правило распознавания текста вместо LLM и не измеряют MLX-модели. Один тест использует управляемые асинхронные ответы провайдеров, чтобы воспроизвести потерю очередной реплики.

| Вход / ситуация | Фактический результат на f71de9d | Владелец исправления |
|---|---|---|
| «Чувствую себя хорошо. А зачем вы спрашиваете?» | Факт пропадает при наличии `user_question` | semantic_bridge, семантический переход |
| «На прошлой неделе чувствовала себя хорошо» | Закрывается вопрос о текущем самочувствии | временной контекст фактов |
| Смысл имеет `subject=unknown` | Факт записывается как относящийся к подопечному | проверка субъекта, FactRecord |
| «Давайте позже, я занята» в середине разговора | Снова задаётся вопрос о самочувствии | глобальные управляющие действия Planner |
| «Нет» на «Удобно поговорить?» | Повторяется тот же вопрос | ответ на активный вопрос |
| «Да» на подтверждение завершения | Возврат к вопросу о самочувствии | контракт ответа, завершение |
| Нет сведений о доставке вопроса | Контекст всё равно сообщает `complete` | журнал доставки, context_builder |
| Старый факт в новом ходе | Ему приписывается ID текущей реплики | происхождение фактов |
| Ситуационное уточнение прервало вопрос о самочувствии | Тип вопроса `risk`, текст — старый вопрос о самочувствии | владение активным вопросом |
| Две реплики обрабатываются одновременно | Вторая теряется после изменения state_version | CallActor, порядок применения событий |

Три контрольные проверки проходят: текущий факт о себе записывается, факт о другом человеке не закрывает поле, «алло» не закрывает поле.

Дополнительно по чтению кода: STT возвращает `GOOD` константой; Renderer получает intent/FSM/planner_text и факты, но не текущую реплику и последовательность разговора; при STT/LLM exception обработчик пишет событие и молча возвращается. Эти наблюдения не являются измерением качества живого звонка.

Источники кода: [semantic_bridge](https://github.com/Belvist/imvera/blob/f71de9d8ba36609b116eb24dd63c7e88a94c05d7/packages/dialogue/semantic_bridge.py), [Planner](https://github.com/Belvist/imvera/blob/f71de9d8ba36609b116eb24dd63c7e88a94c05d7/packages/dialogue/planner.py), [CallActor](https://github.com/Belvist/imvera/blob/f71de9d8ba36609b116eb24dd63c7e88a94c05d7/packages/voice_runtime/call_actor.py), [context_builder](https://github.com/Belvist/imvera/blob/f71de9d8ba36609b116eb24dd63c7e88a94c05d7/packages/dialogue/context_builder.py).

## 3. Решение об архитектуре

Сохранить Python, Asterisk, действующие MLX-адаптеры и PostgreSQL. Доработать текущие пакеты, вводя изменения вертикально в один действующий путь. Новую параллельную систему диалога не создавать.

| Компонент | Единственная ответственность |
|---|---|
| Transport / Asterisk gateway | Корреляция каналов, кодек, аудио, события доставки, завершение канала |
| CallActor | Порядок событий одного звонка, время, отмена исходящего поколения, вызовы провайдеров |
| STT + endpointing | Границы речи, распознанный текст, известные признаки качества |
| Semantic Interpreter — LLM | Предложить структурированный смысл всей реплики с источниками |
| SemanticValidator | Проверить источники, применимость смысла, соответствие вопросу; вернуть неопределённость явно |
| State reducer | Применить проверенные факты, исправления, отказы и события; единственный писатель состояния |
| Planner / ConversationPolicy | Выбрать допустимое следующее действие и единственный вопрос |
| Renderer — LLM | Сформулировать действие естественно с учётом реплики и контекста |
| SpeechValidator | Проверить соответствие разрешённому действию и фактам до TTS |
| Store | Транзакционно сохранить переход, факты и результат без блокировки аудиоцикла |

Два обращения к LLM здесь выполняют разные функции: понимание и формулировку. Они не имеют права менять состояние. Обычный семантически однозначный служебный ответ может использовать проверенную формулировку Planner без второго обращения. Основной свободный разговор проходит через Renderer. Не менять архитектуру ради непроверенного обещания уложиться в одну секунду.

Рассмотренные варианты:

| Критерий | Расширять правила и регулярные выражения | Свободный LLM-chat управляет всем | Выбранный вариант |
|---|---|---|---|
| Свободная русская речь | Требует постоянных частных правил | Потенциал есть, качество нужно измерять | LLM понимает свободную речь, качество измеряется |
| Факты / отказы / исправления | Проверяемы, но хрупко извлекаются | Нет надёжной границы записи | Явный контракт и проверяемые переходы |
| Задержка | Мало вызовов LLM | Обычно один вызов | До двух вызовов; измерение и бюджет обязательны |
| Сопровождение | Растущий список исключений | Сложно воспроизвести неверное решение | Фиксированные границы и журнал решений |
| Модели / стоимость | Зависит от выбранных сервисов | Зависит от выбранных сервисов | Текущие локальные модели; стоимость на разговор измерить |

Перенести это решение в следующий свободный номер ADR как принятое к реализации по поручению Даниила. Синхронизировать противоречащие части ADR-008, не переписывая остальную дорожную карту.

## 4. Состояние разговора и память

Один CallState содержит:

- `call_id`, `tenant_id/family_id`, `person_id`, `state_version`, `last_applied_utterance_seq`;
- жизненный цикл: идентификация, согласие, готовность говорить, разговор, завершение, terminal — как эволюция существующего FSM, а не второй FSM;
- `facts`: текущие подтверждённые наблюдения плюс доступ к их неизменяемым ревизиям;
- `topics`: wellness/mood/sleep/plans со статусами OPEN, FILLED, DECLINED, UNRESOLVED и счётчиком уточнений;
- `active_question`: ID, смысл, ожидаемый тип ответа, фактически озвученный текст, generation/phrase ID, состояние доставки;
- `resume_target`: тема, к которой допустимо вернуться после вопроса пользователя или ситуационного уточнения; это не ещё один активный вопрос;
- актуальная тема беседы, последние реплики, обращения и предпочтения, явно высказанные в этом звонке;
- `observations`: сведения о ситуации без заявления, что помощь или внешняя реакция уже произошла;
- техническое состояние и причина завершения.

Факты: `observation_id`, `source_utterance_id`, `source_quote`, `source_span`, `subject_id/unknown`, `temporal_scope`, `value`, `negated`, `revision`, `supersedes_id`. Цитата относится к исходной реплике, а не к текущей. Сохранить её и исходный текст/ссылку на него. Исправление создаёт новую ревизию и снимает актуальность предыдущей; история не стирается.

Временная применимость задаётся для каждого поля. Самочувствие «на прошлой неделе» не отвечает на «сейчас». Сон «прошлой ночью» применим к вопросу о последнем сне. Не фильтровать всё `past` одним запретом: контракту нужны `last_night`, интервалы либо временное описание с проверкой применимости. При неопределённости сохранить наблюдение отдельно и уточнить, не закрывая текущую тему.

Для контекста LLM передавать последние 6 завершённых обменов и текущую реплику; факты, активный вопрос и неразрешённые ссылки передавать отдельно. Начальный бюджет — 3500 входных токенов с измерением на текущем tokenizer; при переполнении сокращать старую историю, а не текущую реплику, источники спорного факта и вопрос. Число обменов и бюджет настраиваемые.

Саммари старого разговора — подсказка для связности, не источник новых фактов. Между звонками загружать только сохранённые записи разрешённого человека; вчерашнее состояние не объявлять сегодняшним. До проверки идентичности не раскрывать чувствительную историю.

## 5. Единый семантический контракт

Заменить потерю смысла при переходе v2 → legacy. Один `CallSession.handle_user_turn(context, validated_meaning)` обслуживает голос и текстовые тесты. Допустим кратковременный адаптер для совместимости, если он переносит все поля; отдельное правило понимания текста не считается приёмкой voice.

Форма контракта ниже — спецификация интерфейса, не готовый патч:

```python
class UserMeaning:
    utterance_id: str
    based_on_state_version: int
    acts: list[str]  # answer, question, correction, repeat, topic_comment, unclear
    answer: QuestionAnswer | None
    facts: list[FactCandidate]
    corrections: list[CorrectionCandidate]
    questions: list[UserQuestion]
    control: ControlIntent | None
    situation_observations: list[SituationCandidate]
    salient_content: list[EvidenceRef]
    clarification_needed: list[ClarificationNeed]

class QuestionAnswer:
    question_id: str
    kind: str       # identity, consent, can_talk, topic, goodbye, clarification
    polarity: str   # yes, no, unknown, not_applicable
    evidence: list[EvidenceRef]

class ControlIntent:
    kind: str       # stop, revoke, defer, decline_topic, wrong_person, pause
    evidence: list[EvidenceRef]
    target_topic: str | None
```

Все типы реализовать строгими Pydantic-моделями с ограничениями размеров. `acts` и `facts` могут сосуществовать с вопросом и управляющим намерением. Одно `consent_answer` больше не обслуживает identity/can_talk/goodbye. Отказ от темы не равен отзыву согласия на звонки.

SemanticValidator проверяет точные span/quote, принадлежность реплике, субъект и время; исправление должно ссылаться на существующий факт или однозначно описывать его. Неправильный JSON — одна попытка исправления в оставшемся времени; потом событие ошибки и выбранное действие восстановления. Корректный JSON сам по себе не означает корректный смысл.

Короткое «да» применяется только к известному закрытому вопросу с достаточным подтверждением доставки и понятной связью. При partial/unknown не угадывать согласие или завершение. При этом прямое «перестаньте звонить» не зависит от того, дослушан ли вопрос. Не блокировать понятное требование остановиться из-за отсутствия абсолютной ASR-уверенности; спорное распознавание требует осторожного уточнения.

Дать LLM положительные и отрицательные примеры смешанных реплик, исправлений, другого человека, прошлого времени и коротких ответов. Примеры — поддержка общего контракта, а не словарь допустимых фраз.

## 6. Выбор следующего действия — разговорная логика

Planner выбирает действие после применения всех совместимых смыслов реплики. При отзыве согласия прекращается дальнейший сбор; при обычном вопросе пользователя факты из той же реплики не теряются.

Приоритеты:

1. Явное stop/revoke/wrong_person/defer — действуют в любом нетерминальном состоянии. «Нет» на готовность говорить закрывает звонок вежливо. Явное «закончим» не требует обязательной второй просьбы; существующий путь подтверждения также обязан корректно обрабатывать да/нет.
2. Техническая невозможность понять или продолжить — восстановление с ограниченным числом попыток.
3. Ситуация, о которой человек просит рассказать сейчас, и критически неоднозначное сообщение — уместное уточнение; обычная анкета приостанавливается. Наблюдения сохраняются, клинические выводы и сообщения о внешних действиях не генерируются.
4. Прямой вопрос пользователя — короткий ответ по разрешённым сведениям, затем один естественный переход при необходимости.
5. Исправление — применить и кратко подтвердить смысл, не возвращаться к уже исправленному старому факту.
6. Содержательная реплика — отреагировать на неё; выбрать уточнение или развитие текущей темы, если оно полезно человеку или цели звонка.
7. Перейти к следующей незатронутой теме либо завершить разговор с неполным результатом.

Для открытой речи Interpreter может предложить тему и цель уточнения с источником. Planner проверяет: связано ли это с репликой, не повторяется ли вопрос, не ответил ли человек уже, не устал ли он, не исчерпан ли бюджет. LLM не назначает себе инструменты и не пишет в состояние.

`DialogueAction` содержит `intent`, `acknowledge_refs`, `answer_user_question`, `allowed_answer_facts`, `question` (0 или 1), `resume_target`, `forbidden_claims`, `capabilities`, `state_version`. Действия: answer_question, acknowledge_and_follow_up, acknowledge_and_ask_topic, clarify, repair_hearing, repeat_question, wait, close. Это общее множество действий, не набор текстов на каждую фразу.

Темы не являются обязательным порядком wellness → mood → sleep → plans. Если ответ уже содержит сон и планы, они учитываются сразу. Обычно не более двух уточнений подряд по одной неопределённости. После лимита — UNRESOLVED или DECLINED, подходящий переход или завершение; не оставлять скрытый обязательный флаг, который снова вытолкнет на тот же вопрос.

Запрос «не хочу про здоровье» закрывает именно тему как DECLINED. «Я устала» позволяет сократить беседу, а «сейчас не могу говорить» завершает её. Желание человека важнее полноты сбора.

Сведения о продукте хранить в версионированном `ProductBrief`: кто такая Вера, цель беседы, доступные операции. Динамическое «сохранено/передано/назначено» берётся из реальных receipts, а не из сайта или промпта. На вопросы вне разрешённых знаний отвечать честно; не выдумывать погоду, историю пользователя или действие семьи.

## 7. Renderer и контроль озвучивания

Renderer получает **текущую реплику, последние обмены, новые/исправленные факты, последнюю реально воспроизведённую фразу, активный вопрос, выбранный DialogueAction, ProductBrief и фактические capabilities**. Список всех фактов без их изменения в этом ходе недостаточен для естественной реакции.

Выход: `canonical_text`, `question_id`, `used_fact_ids`, `claimed_capability_ids`. Речь обычно занимает одну-две короткие фразы; ограничение длины не реализовывать обрезанием строки посреди слова или вопроса. При превышении — ограниченное переформулирование либо корректная короткая формулировка разрешённого действия.

SpeechValidator проверяет вопрос и его соответствие action, факты/ссылки, отсутствие новых обещаний, чисел и людей без источника, согласованность завершения. Список запрещённых подстрок оставить дополнительной защитой: он не доказывает сохранность смысла. Служебные утверждения о consent, сохранении и внешних операциях строить из проверенных разрешений. Качество парафразов проверяется корпусом и прослушиванием.

Если Renderer недоступен или дважды нарушает контракт, Planner формирует правдивую короткую реплику для текущего действия и явно помечает degraded mode в trace. Это обработка отказа реальной функции, а не подмена основной беседы заготовками. Если TTS не работает, после ограниченной попытки завершить звонок с техническим результатом; не утверждать, что пользователь услышал техническое сообщение.

Один и тот же `canonical_text` передаётся в TTS и журнал. Отдельно хранить generated/sent/playback-confirmed/partial. Наличие текста в истории генерации не означает, что он был воспроизведён полностью.

## 8. Слышать, не перебивать и не терять реплики

Входящая и исходящая ветви имеют отдельные описания sample_rate/codec/channels. Внутри STT — PCM S16LE mono 16 kHz, 20 ms = 640 байт. Частоту входного ресемплера брать из capture; событие inject не имеет права её менять. Имена и формат каналов связывать с конкретным ARI call/channel ID.

Silero VAD — явная настройка профиля. Отсутствие модели не маскировать: профиль либо явно degraded с названием фактического VAD, либо не проходит readiness для требуемого режима. Начальные параметры для проверки, не обещание качества: pre-roll 200–300 ms; кандидат конца фразы после примерно 450–650 ms тишины; дополнительное ожидание до 1000–1400 ms при признаках незаконченной мысли. Проверить медленную речь, «сейчас… подумаю», слова после паузы и шум. Срабатывание VAD не должно дублировать стартовый PCM-кадр.

Partial STT может помогать оценить завершённость, только если настоящий адаптер её поддерживает. Если нет, честно используется сегментное распознавание и учитывается его задержка. Факты коммитятся по final. Не называть финальное распознавание потоком ради отчёта.

STTResult: текст, utterance_id, длительность, доступные признаки речи/клиппинга, provider confidence nullable, `quality=GOOD/LOW/UNUSABLE/UNKNOWN`, основания качества. Убрать константный GOOD. Отсутствие confidence не считать ни высокой уверенностью, ни автоматическим отказом всех реплик. Пороговые решения проверять на записанном корпусе.

После конца вопроса тишина запускает таймер, а не ложный ответ. Начальный профиль: один мягкий вопрос о слышимости через 7 секунд, завершение после дальнейших 15 секунд без ответа; явная просьба подождать переключает в wait и продлевает срок. Это параметры для проверки с целевой аудиторией, а не универсальные значения. Таймер стартует после подтверждённого воспроизведения и отменяется при новой речи.

При начале реальной речи отменяется исходящее поколение: локальная очередь, активная задача TTS, буфер PBX. `FLUSH_MEDIA` — только очистка для прерывания/аварийного сброса. Обычный конец фразы использует завершение потока и подтверждение доставки, а не FLUSH. Согласовать механизм подтверждения с фактически установленной версией Asterisk. PBX acknowledgement — граница наблюдаемости, не доказательство человеческого понимания; слышимость проверяется записью SIP-стороны.

Новая пользовательская реплика получает монотонный sequence и ID **до** запуска асинхронного STT. ASR может работать параллельно, но результаты применяются в порядке реплик одним actor. `state_version` защищает от применения старой интерпретации, но не разрешает выкинуть сказанное человеком.

Порядок обработки:

```python
# Псевдокод внутри единственного владельца состояния.
async def process_next_final_utterance(utterance):
    context = build_context_from_current_committed_state(utterance)
    meaning = await interpreter.interpret(context, timeout=remaining_budget())
    validated = semantic_validator.validate(context, meaning)
    next_state, domain_events = reducer.apply(state, validated)
    action = planner.choose(next_state, context, validated)
    await store.commit_turn(utterance.id, next_state, domain_events, action)
    state = next_state
    if newer_user_speech_exists():
        return  # Отменяется устаревший ответ, НЕ применение фактов пользователя.
    await render_validate_and_speak(action, context, validated)
```

Ошибки провайдеров становятся событиями для Planner. Если контекст изменился по внешнему событию, повторно интерпретировать ещё не применённую реплику на актуальном снимке с ограничением попыток. Не применять её под новым вопросом без сохранения вопроса, который был активен при начале речи. Для этого utterance сохраняет `question_at_speech_start` и delivery status.

Отмена исходящей генерации не удаляет очередь входящих реплик. Уже применённый utterance_id не применяется второй раз. На timeout первого распознавания обработать его ошибку и продолжить очередь, не ждать бесконечно.

## 9. Ошибки, сохранение и несколько звонков

| Событие | Требуемое поведение |
|---|---|
| Пустой результат / шум | Не менять факты и согласие; счётчик ошибки и уместная просьба повторить |
| STT timeout | Ограниченная повторная попытка того же аудио; затем объяснение сбоя, если TTS доступен |
| LLM JSON/timeout | Один retry в оставшемся бюджете; затем действие восстановления, не вечная тишина |
| Renderer error | Проверенная короткая формулировка выбранного действия; событие degraded |
| TTS error | Ограниченный retry; техническое завершение, если звук недоступен |
| PostgreSQL error | Не объявлять сохранение; ограниченная попытка и технический результат |
| Capture disconnect | Отменить работу и завершить текущий call_id, сохранить причину |
| Hangup пользователя | Единственный терминальный результат; поздние ответы не звучат |
| Новая сессия сверх лимита | Контролируемый SIP busy/unavailable; действующий звонок не прерывается |

Store сохраняет исходную реплику, проверенные наблюдения, изменения состояния и решение в одной транзакции с уникальным ключом `(call_id, utterance_id)`. Конкурирующая запись проверяет state_version. Синхронный драйвер не блокирует event loop аудио: допустим имеющийся ограниченный thread pool на переходный период, далее async adapter. Сбой записи не должен оставить опубликованное состояние «успешно сохранено».

Завершение фиксируется идемпотентно: результат один, отдельные события фактического конца playback и отключения транспорта не создают второй результат звонка. После перезапуска восстановить сохранённое состояние/наблюдения; оборванный SIP-звонок не изображать продолжающимся. Отзыв согласия хранится на уровне человека; любое последующее планирование/допуск обязано его учитывать, когда будет подключено.

На локальном M5 оставляем заявленный лимит 1 до замера. Однако уже сейчас все словари, очереди, provider request IDs, состояние и аудиоканалы изолируются по call_id и tenant/person binding. Убрать выбор «последней сессии» и удаление действующей сессии при новом звонке. Локальный лимит проверяется при admission.

Для переноса на сервер сохраняется тот же контракт: SIP/media gateway маршрутизирует звонок на одного actor-владельца; inference workers имеют bounded queues и отдельный admission. Ёмкость CPU/GPU определяется нагрузочным тестом, а не числом запущенных HTTP-процессов. Один owner с fencing/lease нужен при нескольких runtime-узлах; внедрять его при фактическом горизонтальном развёртывании. Нынешняя приёмка одного звонка не доказывает готовность к массовому трафику.

## 10. Наблюдаемость и скорость

В trace каждого хода: SHA/config/model revisions, call_id, utterance_id/sequence, capture format, audio interval, STT text/quality basis, вопрос на старте речи и его delivery, semantic payload, validated/rejected facts с причиной, state version до/после, выбранное действие с кратким reason code, canonical text, TTS request/text hash, generation ID, playback evidence, persistence receipt, outcome.

Никаких скрытых рассуждений модели в обязательных логах: нужны решение и проверяемые основания, например `USER_QUESTION_FIRST`, `TEMPORAL_SCOPE_MISMATCH`, `TOPIC_DECLINED`. Записи разговоров и полные тексты — ограниченный диагностический доступ и настраиваемое хранение, не бесконечный общий лог.

Замерять `speech_end → first audible assistant audio` по записи получающей стороны, включая endpointing, ASR, очереди, interpretation, policy/store, render, TTS и транспорт. Отдельно полезный ответ и техническое сообщение; не улучшать показатель фразой «секундочку», скрывая реальную задержку.

Цели существующего проекта: p50 < 1 s, p95 ≤ 2 s; прекращение звука при перебивании p95 < 250 ms. Это цели, **не текущие измерения**. На Mac получить исходные значения на минимум 100 содержательных ходах и отдельно cold/warm. Не складывать stage p95 как будто это измеренный end-to-end p95. Если цели не достигнуты, показать вклад этапов, затем исправить главный вклад, сохранив качество.

Сначала сократить лишний контекст, повторную загрузку, холостые стадии приветствия и полные повторные запросы. Не ввести одновременно три новых модели. Настоящий streaming TTS выдаёт первые доступные PCM-чанки; HTTP stream, содержащий единственный полный результат, помечается как buffered. Объём допущенных запросов ограничить, очередь по требуемой задержке; shared модель не запускать конкурентно без подтверждённой поддержки.

## 12. Приёмка целого разговора

Приложенные 13 тестов — начальный барьер, не полный корпус. После изменения DTO можно переписать их на новый API, сохранив проверяемое поведение. Удалить смысл проверки или пометить xfail ради зелёного отчёта нельзя.

Три уровня запуска:

1. Детерминированные многоходовые проверки состояния: правильный структурированный смысл подаётся в production reducer. Проверяется программа.
2. Записанные WAV подаются в настоящие STT → Interpreter → reducer → Planner → Renderer → TTS. Проверяются модели и интеграция, без SIP.
3. Реальный SIP-клиент звонит на тот же номер/dialplan, отправляет WAV и записывает полученное аудио. Затем свободные разговоры через Zoiper. Прямая отправка текста в API или MEDIA_START smoke не закрывает этот уровень.

Начальный обязательный корпус: не менее 20 разных многоходовых сценариев, не менее 100 пользовательских ходов, несколько вариантов формулировок и несколько голосов/темпов в акустическом наборе. Десять живых/реальных SIP-разговоров, из них минимум три свободных разговора с человеком; длительность по ситуации, несколько полных разговоров по 3–5 минут. Цель — проверить связность, а не удерживать человека ради секундомера.

| Сценарий | Ожидаемое поведение |
|---|---|
| Идентичность и собственное согласие | Нет ложного согласия; после служебного этапа сразу содержательный вопрос без пустого ожидания ответа на второе приветствие |
| Несколько фактов за раз | Все подходящие сведения учтены; повторно не спрашиваются |
| Факт + вопрос «зачем?» | Факт сохраняется, на вопрос даётся ответ |
| Факт + «кто вы?» | Ответ о Вере, факт не исчезает |
| Исправление после смены темы | Обновляется исходное наблюдение с ревизией |
| Другой человек / прошлое | Нет присвоения текущего состояния подопечному |
| «Да / нет / угу / алло» | Привязка к реальному вопросу; отсутствие угадывания факта |
| Вопрос вне знаний | Правдивое ограничение без выдумки |
| Личная история | Уместная реакция, одно развитие темы, плавный возврат |
| «Не хочу об этом» | Отказ от темы принят, повторного давления нет |
| «Не сейчас» / «закончим» | Завершение из любого этапа |
| «Больше не звоните» | Отзыв не путается с отказом от одной темы |
| «Нет» на готовность говорить | Нет повторения того же вопроса |
| Да/нет на подтверждение завершения | Завершение или продолжение согласно ответу |
| Медленная речь и пауза | Не обрезать мысль; не считать паузу ответом |
| Неясная речь несколько раз | Ограниченные уточнения, затем осмысленный переход/завершение |
| Две реплики подряд | Сохраняется смысл обеих, устаревший ответ не звучит |
| Перебивание на вопросе | Текущий вопрос не становится автоматически complete |
| Ситуационное уточнение | Правильный вопрос и субъект; нет выдуманной передачи/помощи |
| Сбой каждого провайдера и БД | Нет бесконечной тишины или ложного успешного результата |
| Разрыв/перезапуск | Один результат, сохранённые факты доступны |
| Второй звонок при лимите 1 | Первый разговор не меняется; второй контролируемо отклонён |

Автоматические release gates для этого корпуса: ноль потерь применимых фактов на детерминированном пути, ноль ложных consent/control/family-delivery claims, ноль применений чужого/прошлого как текущего, ноль перепутанных сессий. Для реальных моделей целевой уровень корректных смысловых решений ≥95% на размеченных ходах; отдельно считать критические ошибки и причины, не прятать их в среднем проценте. Это порог данного корпуса, не оценка всего возможного языка.

Связность оценивается человеком по фактической записи: отвечает ли Вера на текущую мысль, помнит ли исправления, уместно ли уточняет, не повторяет ли анкету, соблюдает ли отказ. Каждый провал сопровождается call_id/turn_id, ожидаемым действием и первым неверным решением. Самооценка LLM — вспомогательная, не единственный вердикт.

Публикуемый отчёт: SHA/config/model revisions, команды и exit codes, количество сценариев/ходов/звонков, регрессии, реальные записи и traces, p50/p95 с определением выборки, непроверенные ограничения. Health endpoints и число unit tests вынести в техническую часть, не использовать как доказательство разговора.

## 13. Пример целевого поведения

Это сценарий приёмки, **не запись работающей системы**. Согласие и идентичность уже подтверждены.

Вера: «Как вы себя чувствуете сегодня?»

Человек: «В целом нормально. Только плохо спала, до двух читала. А зачем вы спрашиваете?»

Вера: «Я разговариваю с вами о том, как проходит день. Что вы читали?»

Ожидание состояния: wellness и sleep учтены; вопрос о цели отвечен. Выбор развития темы чтения допустим; повторно спрашивать «Как вы спали?» нельзя.

Человек: «Детектив. Только я оговорилась: до двенадцати, а не до двух».

Вера: «Поняла, до двенадцати. Детектив оказался интересным?»

Ожидание: исправлена конкретная деталь, а не настроение. Исходная ревизия сохранена.

Человек: «Да. Сегодня хочу прогуляться, настроение хорошее».

Вера: «Куда хочется прогуляться?»

Ожидание: plans и mood учтены, разговор развивается по ответу. Допустима другая короткая уместная формулировка.

Человек перебивает: «Хотя про планы не хочу. Давайте закончим».

Вера: «Хорошо. До свидания».

Ожидание: отсутствует новый вопрос; финальная фраза не обрезана, итог сохранён один раз. Нельзя продолжать ради обязательных полей.

## 14. Граница готовности

После прохождения всех уровней можно сообщить: «проверен этот голосовой контур на таком-то профиле и такой-то нагрузке». Нельзя из этого вывести готовность семейных уведомлений, медицинской помощи, массового обслуживания или идеальное понимание любой речи.

Этот проект закрывает архитектурные решения для текущего задания. Частные ошибки дальше разбираются по trace и включаются в общий корпус, а не требуют от Даниила каждый раз заново изобретать поведение продукта.
